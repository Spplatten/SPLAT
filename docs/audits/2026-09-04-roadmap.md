# SPLAT future planning and acceptance gates

Proposed plan based on the [technical audit](2026-09-04-clinical-audit.md) and [competition/scope audit](2026-09-04-competition-and-scope.md). These are suggested priorities and target windows, not authorized implementation, delivery promises or evidence of completion. No assignees, team capacity or budget were supplied; owners below are roles to assign.

**First objective: one external client can request an approved action, and the resulting execution cannot exceed that approved policy.** Every other deliverable depends on that contract. Work on truthful status and documentation can proceed alongside containment repairs; new execution breadth should wait.

## Immediate release controls

1. Gate or disable generic `run_command`/`run_code` and strict-isolation claims until F01-F12 pass. Keep explicitly supported diagnostic evaluation available under its actual permissions.
2. Prevent UI/API success claims for absent services, placeholder HTTP/OAuth/ReAct work, failed tool execution or rejected analysis. Do not index such results as accepted evidence.
3. Correct security/evidence/competitive assertions and the ROI example. Label Windows network exemptions, historical evidence and unproven end-to-end paths precisely.
4. Triage the affected native SQLite dependency and out-of-support Windows App SDK. Include the .NET 9 support deadline in release planning.

Kernel, Windows, data-integrity and result-truth work can run in parallel once owners agree on the threat model and policy/result schema. Do not parallelize incompatible protocol changes without a shared contract. A new transport cannot compensate for missing authorization or expiry semantics.

## Day 1-30: establish the boundary

Concentrate on packages 1-8 and dependency triage. Write a versioned capability manifest consumed by UI, MCP descriptions, docs and test selection. Separate at least: trusted local diagnostic, strict Windows-contained diagnostic and supported Linux leased execution. A runtime must reject a requested permission it cannot enforce.

Exit gate:

- A fresh supported host runs one real allowed action and denied executable/file/network cases **through the external client**, not just the daemon harness.
- At least 100 repeated runs of this supported scenario have no unexplained permission widening. This is an initial regression target, not a statistical safety proof.
- Concurrent A/B leases cannot influence each other's permitted operations.
- Cancellation, expiry, lost client, failed response write, parent death and daemon restart have measured cleanup behavior. Proposed target: no surviving workload processes within two seconds of a termination decision; publish actual measured distributions and fail if the agreed bound is missed.
- Receipt records identify source/build/policy hashes, actor, runtime, effective controls, execution outcome and cleanup result. An unavailable health component prevents execution.
- No accepted diagnosis or memory insertion occurs on tool/analysis failure; sentinel secrets do not cross unauthorized outputs.

If the guest privilege boundary cannot be demonstrated, keep Linux arbitrary-code execution unavailable and ship the narrower supported Windows diagnostic contract. Do not spend the next month adding orchestration to hide that failure.

## Day 31-60: establish adoption and independent evidence

Build one authenticated n8n adapter, one local MCP integration and the minimum operator UI needed to review a policy and its result. Agree retry semantics: a caller-supplied idempotency key must not duplicate a state mutation. Treat an uncertain previous outcome as uncertain until reconciled.

Exit gate:

- Three clean machines reproduce install, first approved action, denial, update and uninstall with documented administrator provisioning. Proposed assisted setup target: 30 minutes or less after prerequisites; measure prerequisite effort separately.
- Both clients produce joinable principal/mission/policy/outcome records and reject attempted policy expansion.
- An independent verifier on a different machine verifies an exported receipt and detects an altered payload, invalid signature, truncated/replaced history against a retained checkpoint and unauthorized redaction.
- Fresh cold/warm p50/p95/p99 measurements cover the actual supported client-to-executor path, with hardware, policy, workload, sample count, failures and raw records. Keep the existing Windows-only benchmark scoped to its measured path.
- Five target-buyer interviews and two design-partner pilots validate the same concrete use case. Do not use sensitive customer data to compensate for a missing synthetic/adversarial test harness.

## Day 61-90: establish value and supportability

Run one repeated, useful workflow with two pilot teams for four weeks. Track actual avoided operator effort, remediation correctness and operational support cost. A fleet/marketplace decision follows this evidence.

Exit gate:

- At least 100 representative missions per team, with a proposed supported-task completion target above 95%; report provider outages and unsupported requests separately, not silently removed from the overall operational record.
- Zero unresolved critical/high boundary findings for the released capability; an independent security review covers the execution and evidence trust model.
- Upgrade/recovery/key rotation/credential revocation are rehearsed; support ownership, rollback limits and supported host versions are documented.
- Record all-in cost and minutes saved; seek one paid continuation based on measured value. Do not reuse the incorrect repository ROI calculation.
- Add workspace file transactions only if customers value them and atomic commit, rejected mutation and external-side-effect limitations have a tested contract.

## Suggested policy and evidence contract

| Field group | Minimum contents | Purpose |
| --- | --- | --- |
| Request identity | Principal and auth provenance, request/idempotency ID, approval reference, policy version/hash | Prove who authorized this specific action and prevent replay/permission substitution. |
| Effective permission | Executable identity and argument vector; workspace object/mount boundary; protocol/address/port rules; runtime UID/capabilities; resource and duration ceilings | Describe what the runtime actually permits, including any explicitly unsupported dimension. |
| Enforcement state | Build/kernel identifiers, attached controls, cgroup/job identity, effective read-back limits, admission verdict | Prevent policy intent from being mistaken for installed enforcement. |
| Outcome | Started/failed/refused/expired/cancelled/uncertain/completed state, exit code, output provenance/redaction state, quality acceptance | Let callers make safe retry and downstream-memory decisions without parsing prose. |
| Cleanup | Parent/descendant termination, policy removal order, workspace disposition and residual resources | Establish that expiry or disconnect did not leave authority running. |
| Integrity | Versioned algorithm/key ID, payload commitments, authenticated retention events and independent checkpoint/signature | Make evidence portable and define its actual tamper/rewrite/truncation guarantees. |

Do not store raw secrets, full bearer tokens or unnecessary personal data in receipts. Key custody and independent checkpoints need a stated threat model; keeping a key beside a mutable database does not provide independent verification.

## Verification matrix to add

| Area | Required adversarial scenarios |
| --- | --- |
| Identity | Invalid/expired/revoked credential before every side effect; second local user; replay; credential rotation mid-session. |
| Linux admission | Missing BPF/LSM, failed map writes, unsupported kernel, failed cgroup placement/controller writes, malformed policy and oversized request. |
| Lease isolation | Concurrent conflicting grants, shared inode/IP, revoke A while B runs, inode replacement, interpreter/native child and host-control access. |
| Lifecycle | TTL overrun, forked descendant, early parent exit, lost client, output backpressure, failed audit sink, daemon crash/restart and host shutdown. |
| Filesystem | Outside workspace, junction/symlink/reparse race, cross-jail read/write, read-only mutation, failed cleanup and approved file commit. |
| Network | Allowed and denied IPv4/IPv6, TCP/UDP, wrong port, DNS changes, inherited/preconnected descriptors, local sockets and direct-IP traffic. |
| Results/AI | Empty telemetry, nonzero exit, timeout, invalid schema, all candidates rejected, model unavailable, unsupported node, unknown cause and unsafe suggested remediation. |
| Privacy/evidence | Secrets in stdout/stderr/errors/MCP arguments; payload-only changes; downgrade; missing/wrong/rotated key; authorized redaction; truncated and replaced history. |
| Workflow/integration | Real UI-created graph, branch preservation, restart/resume, duplicate trigger/idempotency, cancellation propagation, OAuth rejection/timeout and adapter transport negotiation. |
| Release | NuGet/Rust/Python dependency review, native library version, signed artifact verification, clean-machine standard-user flow, rollback/update/uninstall and documented prerequisite failures. |

Run tests appropriate to each changed seam; an implementation-mirroring mock is insufficient where the claimed property is OS enforcement. Keep unsafe kernel/escape probes in disposable supported environments with an explicit test harness and no customer workload.

## Decisions that would change this plan

- **Buyer cannot deploy WSL/kernel prerequisites:** narrow to Windows diagnostics or a separately managed execution environment; do not promise same-host arbitrary-code isolation on unsupported machines.
- **Hardened alternatives already solve the chosen job:** integrate them and retain only a proven policy/evidence advantage, or stop that product branch.
- **No paid value after two prototypes and five interviews:** revise the buyer/job before expanding fleet management, billing or connectors.
- **User demand is genuinely workflow authoring:** adopt a mature workflow engine and preserve SPLAT as an execution adapter; budget durable state, OAuth lifecycle and connector maintenance explicitly.
- **Healthcare use becomes a concrete intended use:** define that use, data flow, accountable operator and clinical validation requirements in a separate scoped assessment. Current computer-diagnostic labels and security tests do not establish medical suitability.

The next implementation unit should be **F01: authenticate before dispatch, with a regression that asserts no side effects**. In parallel, resolve the evidence verifier and Linux fail-closed admission/lifecycle contracts. The audit is complete as an assessment; the fixes and proposed release gates remain outstanding.
